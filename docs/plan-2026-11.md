# Plan, November 2026: work the inbox and make it routine

Supersedes `docs/handoff.md` (21 September), deleted in 2.15.2. Read AGENTS.md sections 6 and 7 first.

## Why this plan exists

The crew's design is sound and matches current guidance (hooks for hard
rules, interview before big work, review against the plan, evals before
words). What stalled is the loop: 15 field reports filed between 25
September and 7 October, plus `docs/field-reports/001`, and none worked.
The scoreboard stops at 2.15.1.

The loop stalled because it is priced per report: seed, reproduce, case,
fail, edit, suite, row, for every miss. Sixteen reports at that price is
sixteen evenings. The reports cluster into five patterns, and a pattern
is what a case measures. So the unit of work becomes the cluster.

Two environment checks are already done (8 November, real session on
the Windows laptop): background subagents keep Bash, and the guards fire
inside agents on native Windows (`PreToolUse:Bash`, `[crew hook:
guard_db]`). Nothing needs changing for either.

## The standing system (simplified 8 November)

Decided after the first cluster run: the plugin is not the complicated
part, the measurement around it was. Hooks, Articles, Captain and
`/field-report` stay as they are. The loop gets lighter.

1. **Inbox.** Issues labelled `field-report`, or a numbered file in
   `docs/field-reports/`. Unchanged.
2. **Ledger.** `docs/field-reports/LEDGER.md`, one row per report. The
   closing comment on an issue is its row.
3. **Facts go in the same day.** A report that is a missing piece of
   Django knowledge or a hygiene rule becomes one line in the Articles or
   the Captain, paid for by a cut, with no case and no eval run. Commit,
   bump the patch version, close the issue.
4. **Judgment misses wait for a pattern.** They sit in the ledger as
   `clustered` until three share one. Then one case, one run at one run
   per arm, and one edit only if the crew arm fails and the baseline does
   not. If both arms pass, the model already does the job: close the
   reports as found by the model, keep the case as a regression guard,
   and change nothing.
5. **Evals are a smoke test, not a gate.** The suite runs when agent
   prose changes, one run per arm, never three by default. The delta is
   read as a cut signal: a case the baseline passes is a reason to
   shorten that agent, not lengthen it. The roster is expected to shrink
   as deltas close; eight agents is the ceiling, not the target.
6. **Tool.** `/work-the-inbox` at the repo root runs the above and stops
   at each eval checkpoint. Evals run on Actions; nothing needs the
   laptop.
