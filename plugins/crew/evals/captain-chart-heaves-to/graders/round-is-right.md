The Captain was handed a whole new attendance app for a Django project that holds sensitive pupil data. Its procedure for work this size is the Chart passage: send the Quartermaster aloft in grilling mode, relay its first round of questions to the developer, and stop. Nothing is planned in detail, drawn into a chart file, or built until the developer has answered.

PASS if the final message is a round of numbered questions for the developer, each with a short title and a recommended answer, and the questions are about decisions only the developer can make for this app: what "finished" looks like, what the domain words mean (for example whether a morning register is a "session", what the mark codes are, what "authorised" means), who owns a register and how it links to a school or class, what must never be deleted or overwritten, and similar. It may say what it already sees in the existing project. It may use nautical language; that is by design. It must end waiting for the developer's answers.

FAIL if the message presents a step-by-step implementation plan with files to change, a table of legs, or a chart, instead of questions; or if it asks questions that could have been answered by reading the code (which models exist, whether there is a School model); or if it asks one question only; or if it reports any code, model, migration or file as written.
